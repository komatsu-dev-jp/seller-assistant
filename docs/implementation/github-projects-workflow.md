# GitHub Projects 運用

## 結論

`AI App Delivery` は、複数アプリの作業を一つの表とボードで管理する GitHub Project（GitHub上の進捗管理表）です。`seller-assistant` では、Issue（作業依頼票）・Pull Request（変更内容の確認単位）・仕様書・承認証跡をこのProjectに結び付けます。

- Project: <https://github.com/users/komatsu-dev-jp/projects/1>
- このリポジトリ: `komatsu-dev-jp/seller-assistant`

## どれを正本にするか

| 情報                                     | 正本                   | 役割                                                         |
| ---------------------------------------- | ---------------------- | ------------------------------------------------------------ |
| 作業の進捗、担当モデル、レビュー、承認   | GitHub Project         | 全アプリを横断して見渡す。                                   |
| 作業の目的、受け入れ条件、会話に近い文脈 | GitHub Issue           | 1つの作業単位を定義する。                                    |
| 実際に変更した内容とテスト結果           | Pull Request           | 変更を独立に確認する。                                       |
| 詳細な仕様・設計・受け入れ条件           | `docs/`                | 実装時の正本。Projectにはリンクだけを置く。                  |
| 重大または再発し得る失敗                 | `memory/incidents/`    | 候補記録から、検証済みlessonへ昇格する。                     |
| 利用者の最終承認                         | Slackの明示返信とIssue | 既存の承認チャンネルと証拠のリンクを使う。自動送信はしない。 |
| Notion                                   | 必要な場合の限定ミラー | 仕様や業務データの正本にはしない。                           |

Obsidianを使う場合も、`docs/` と `memory/` を同じGitリポジトリから開くだけにします。Obsidian独自のコピーを正本にしません。

## Projectの項目

| 項目               | いつ設定するか             | 使い方                                                                                                                                            |
| ------------------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status             | 作業開始から完了まで       | `Inbox` → `Ready` → `In Progress` → `In Review` → `Done`。判断待ちや原因不明は必ず`Blocked`にする。                                               |
| リスク             | Solの計画時                | `Low`、`Medium`、`Critical`から選ぶ。DB、権限・個人情報、在庫競合、会計計算、承認状態、外部連携、元に戻せない変更は少なくとも`Medium`として扱う。 |
| 実装モデル         | Solの計画時                | `Luna max`、`Terra`、`Sol max`の実装担当を先に決める。                                                                                            |
| Sol ゲート         | 計画から最終確認まで       | `未実施` → `設計済み` → `最終レビュー中` → `承認済み`。修正が必要なら`要修正`に戻す。                                                             |
| 利用者承認         | 承認が必要な作業           | `不要`、`確認待ち`、`承認済み`、`差し戻し`を明示する。                                                                                            |
| 仕様・実装パケット | Solの詳細設計後            | `docs/`内の仕様、設計図、受け入れ条件、手順、テスト計画へのリンクを置く。                                                                         |
| 学び・失敗ログ     | 重大または再発し得る失敗時 | `memory/incidents/`の候補記録、または昇格済みlessonへのリンクを置く。                                                                             |

## モデルの振り分け

Sol maxは、各作業を細かく分け、実装者が迷わない「仕様・実装パケット」を作ります。パケットには、変更対象、対象外、受け入れ条件、テスト、失敗時の停止条件、データ・権限への影響を含めます。

| 担当     | 任せる内容                                                                                   | 必須条件                                                                                                   |
| -------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Luna max | 画面実装、CSS調整、定型API、テスト追加、文書更新                                             | Solのパケットに従う。仕様矛盾・原因不明の失敗・高リスク変更に遭遇したら、推測で続けず`Blocked`にして戻す。 |
| Terra    | 範囲が固定されたAPIやDB変更、実装パケットに沿った中程度以上の変更                            | Solの設計と最終レビューを必須にする。                                                                      |
| Sol max  | 調査、設計、リスク判定、DB・権限・個人情報・在庫競合・会計・承認状態の判断、独立最終レビュー | Criticalでは必須。Mediumでも設計と最終レビューを基本にする。                                               |

実装モデルは「最も安いモデルを選ぶ項目」ではありません。Solが設計で安全に分割した後に、限定された実装をLuna/Terraへ渡して費用を抑えるための項目です。

## 1件の作業を進める手順

1. GitHubの「New issue」から`実装パケット`または`不具合・安全停止`を選び、Issueを作成します。
2. Issueを `AI App Delivery` に追加し、`Status: Inbox` にします。
3. Sol maxが調査・設計を行い、リスク、実装モデル、仕様・実装パケット、Sol ゲートを設定します。
4. パケットがそろったら`Ready`にします。Luna/Terraは、この状態の限定作業だけを実装します。
5. Pull RequestをIssueへリンクし、`In Review`へ進めます。テスト、承認済みモックとの比較、Solの最終レビュー、必要ならSlackの利用者承認を記録します。
6. 必須の確認がそろったら`Done`にします。不明点・仕様矛盾・原因不明の失敗は、完了にせず`Blocked`に戻します。

GitHub CLIを使える環境では、IssueまたはPRをProjectへ次のように追加できます。

```powershell
gh project item-add 1 --owner komatsu-dev-jp --url https://github.com/komatsu-dev-jp/seller-assistant/issues/123
```

## 失敗を記録して再発を防ぐ流れ

軽微で一過性の失敗は、IssueとPull Requestの検証記録だけで十分です。重大または再発し得る失敗は、次の順で扱います。

1. 作業を`Blocked`にし、影響範囲を安全に切り分けます。
2. `memory/_templates/incident.md` から `memory/incidents/INC-YYYYMMDD-NNN-...md` を作成し、`status: candidate`で残します。秘密情報、個人情報、実データ、生ログは書きません。
3. Projectの`学び・失敗ログ`へ候補記録のリンクを設定します。
4. 原因、予防策、検証証拠、重複確認、独立レビューがそろった場合だけ、`memory/_templates/lesson.md`でlessonへ昇格します。
5. `memory/INDEX.md`には`status: active`のlessonだけを追加します。未検証の推測は追加しません。

## このリポジトリでの禁止事項

- Project、Issue、Pull Request、Slack、Notionに秘密情報・個人情報・実データ・生ログを残さない。
- 自動出品、画面スクレイピング、非公開API、無人の価格変更を作業項目としても実装しない。
- この変更ではGitHub Actionsのトリガーを追加・変更しない。現行の`.github/workflows/ci.yml`はPull Requestと`main`へのpushで自動実行するため、手動実行だけとする既存の0円運用方針と矛盾している。判断は[Issue #6](https://github.com/komatsu-dev-jp/seller-assistant/issues/6)と`inbox/2026-08-21-github-actions-policy-conflict.md`で保留中であり、利用者の決定まで新たな自動化やworkflow変更を行わない。
