# フリマ物販業務アプリ｜サービス調査メモ

調査日: 2026-08-13（JST）  
状態: UI方向性を選ぶ前の調査。事実・推論・仮説を区別して記載する。

## 結論

進める価値がある案は、規約リスクの高い「メルカリ画面の全自動操作」ではなく、商品1点を中心に、仕入れ、証憑、撮影、採寸、説明文候補、承認、出品引き渡し、在庫、配送、利益、帳簿資料を一つにつなぐ業務基盤である。

最初に検証することは、既存の写真自動化を10商品で実運用しながら、1商品あたりの撮影開始から「本人が出品できる状態」までの時間、修正回数、誤入力件数を測ること。個人版メルカリは本人による最終操作を残し、正式な自動連携はメルカリShopsの契約済み公式APIだけを対象とする。

## 一文の企画

中古衣料を扱う個人事業者と小規模チームが、iPhoneで現物を見ながら正確な商品データを作り、PCで承認・在庫・配送・収益・帳簿資料まで追跡できる、規約準拠を優先した物販業務アプリ。

## 対象利用者

### 最初の利用者

- 月30〜300点ほどの中古衣料を仕入れて販売する個人事業者
- 撮影や採寸を家族・外注者へ任せたい小規模事業者
- Notion、Google Drive、iPhoneショートカット、表計算を行き来している人

### 利用場面

- 撮影場所でiPhoneを片手に、商品を1点ずつ登録する
- PCで複数商品の不足項目、画像、利益、進行状況をまとめて確認する
- 外注者へ「撮影だけ」「採寸だけ」「梱包だけ」の作業を渡す
- 月末に売上、仕入れ、送料、手数料、証憑を確認し、会計ソフトまたは税理士へ渡す

## いちばん強い課題

現在の作業は、写真、手入力、定型文、Notion、メモ、Google Drive、メルカリ画面が分かれている。商品コードを軸にした一つの記録がないため、転記、抜け漏れ、外注時の権限過多、利益計算の根拠不足が起こりやすい。

## 重要な確認結果

### 1. 個人版メルカリの自動化境界

確認できた事実:

- 現行利用規約は、メルカリが指定する法人以外の事業者にメルカリShopsの利用を求めている。
- メールアドレス、パスワード等を第三者に利用させることは禁止されている。
- 第三者への取引代行、代理出品、他人のアカウント利用は禁止行為に含まれる。
- 個人版メルカリの一般公開された出品・価格変更APIは確認できない。
- 公式アプリには下書きと自動値下げがあるが、以前の「まとめて値下げ」は終了している。

設計判断:

- 個人版向けは、写真・文章・価格候補の準備、コピー、ファイル書き出し、公式画面を開くところまでにする。
- 最終保存、出品、値下げ、コメント、取引メッセージ、発送通知は本人が公式画面で行う。
- パスワード、Cookie、SMS認証番号を取得しない。非公開API、通信模倣、クラウド上の自動ブラウザ操作を使わない。

参考:

- [メルカリ利用規約](https://static.jp.mercari.com/tos)
- [禁止されている行為](https://help.jp.mercari.com/guide/articles/647/)
- [アカウントの不正利用](https://help.jp.mercari.com/guide/articles/874/)
- [出品ホーム・下書き](https://help.jp.mercari.com/guide/articles/927/)
- [公式の自動値下げ](https://jp-news.mercari.com/info/31261)
- [まとめて値下げ機能の終了](https://help.jp.mercari.com/guide/articles/673/)

### 2. メルカリShopsなら正式な自動連携が可能

確認できた事実:

- メルカリShopsには商品、在庫、注文、発送、メッセージ、Webhookを扱えるGraphQL APIがある。GraphQL APIとは、必要なデータを指定してサービス同士をつなぐ公式の窓口である。
- 商品を非公開状態 `UNOPENED` で作り、人の承認後に公開状態 `OPENED` へ変えることができる。
- スタッフアカウントと役割が公式に用意されている。
- API利用では、契約時に付与される `API_CLIENT_NAME` が必要と案内されている。一般向けSaaSとして本番利用する前に、メルカリとの契約・承認確認が必要である。
- 本番商品を出さずに試すSandbox（開発用の安全な試験環境）がある。

設計判断:

- MVPではSandboxとモックデータだけを実装対象にする。
- 契約前は実ショップへ書き込まない。
- 本番連携後も、商品は非公開で作成し、責任者の承認後だけ公開する。
- 外注者は自社アプリの最小権限と、必要な場合のみ各自のShopsスタッフアカウントを使う。

参考:

### 3. Chrome拡張「フリマアシスト」の仕組み

確認できた事実:

- Chrome Web Store掲載版は、出品・更新日時、外部検索、定型文、コピー出品、CSV等を案内している。
- 現行の公式掲載に「一括値下げ」は確認できない。
- Chrome拡張は、許可されたWebページのDOMを読む・変更するcontent scriptを使える。DOMとは、Web画面の入力欄やボタンを部品として扱う仕組みである。
- Chrome Web Store掲載はGoogleの拡張機能審査であり、メルカリからの提携・承認を示すものではない。

推論:

- フリマアシストは、公式APIよりも、対象ページへコードを差し込み、画面要素の読み取り、ボタン追加、入力補助、タブ操作をする方式である可能性が高い。
- メルカリから許可を得ている証拠は公開資料では確認できない。未許可と断定する資料もないため、正確な表現は「承認状況不明」である。

設計判断:

- Chrome拡張を作る場合も、読み取りと利用者が押した時の入力補助に限定し、隠れた通信や検知回避をしない。
- MVPの中核をChrome拡張にしない。個人版メルカリの画面変更や規約変更でサービス全体が止まるためである。

参考:

- [フリマアシスト Chrome Web Store](https://chromewebstore.google.com/detail/%E3%83%95%E3%83%AA%E3%83%9E%E3%82%A2%E3%82%B7%E3%82%B9%E3%83%88/jcbljdgnpcckiamdgmnfhijgkkaogmgg?hl=ja)
- [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)
- [Chrome拡張の権限](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)
- [Chrome Web Storeの審査](https://developer.chrome.com/docs/webstore/review-process)

### 4. 税務AIの境界

確認できた事実:

- 他人の求めに応じて反復継続して税務代理、税務書類の作成、税務相談を行うことは税理士業務に当たり、必ずしも有償である必要はない。
- 個人事業者は、収入・必要経費の帳簿と、請求書・領収書等を整理して保存する必要がある。
- 電子取引の証憑は、一定の要件に従って電子データのまま保存する必要がある。

設計判断:

- AIは、事実の抽出、合計計算、重複・不足検知、ユーザーまたは税理士が承認したルールによる仕訳候補、根拠表示、会計ソフト用CSVまでに限定する。
- 個別の税区分判断、節税助言、申告可否の断定、他人の確定申告書作成・提出は行わない。
- UIには「候補」「要確認」「根拠」「承認者」を常に表示する。

参考:

- [国税庁・税理士業務](https://www.nta.go.jp/law/tsutatsu/kihon/zeirishi/02.htm)
- [税理士でない人による他人の申告書作成](https://www.keisan.nta.go.jp/r7yokuaru_sp/cat1/scid2530.html)
- [個人事業者の記帳・帳簿保存](https://www.nta.go.jp/taxes/shiraberu/shinkoku/kojin_jigyo/index.htm)

### 5. 外注と個人情報

確認できた事実:

- 個人データを外注先へ扱わせる場合、委託先の選定、契約、安全管理措置、取扱状況の把握、必要に応じた監査が求められる。
- 仕入れた中古品を継続して販売する場合、古物商許可、相手方確認、帳簿、Web上の公安委員会名・許可証番号・氏名等の表示を確認する必要がある。

設計判断:

- 撮影、採寸、検品、出品準備、承認、発送、経理を役割別に分ける。
- 購入者住所は発送担当にだけ期限付きで表示し、CSVや通知本文へ含めない。
- 誰が、いつ、何を見て、変更し、承認したかを監査ログへ残す。
- 外注終了時の一括失効、再委託の禁止または事前承認、データ削除確認を用意する。

参考:

- [個人情報保護委員会・通則編](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)
- [警視庁・古物商許可申請](https://www.keishicho.metro.tokyo.lg.jp/tetsuzuki/kobutsu/kaisetsu/kobutsu_shinsei.html)

## 競合・代替手段

| 種類 | 強み | 弱み・リスク | このサービスの差別化 |
|---|---|---|---|
| iPhoneショートカット + Notion | 低コスト、すぐ直せる | 手入力と転記が多く、外注権限と監査が弱い | App Intentsで同じ操作を残しつつ、商品コードで全工程を結ぶ |
| フリマアシスト | 無料、画面内の補助が手軽 | iOS非対応、画面変更依存、承認状況不明 | 出品画面だけでなく仕入れから帳簿資料までを管理 |
| メルサポ等の自動操作拡張 | 一括値下げ、再出品、コメント | 個人版規約、誤操作、アカウント制限のリスク | 個人版は本人操作、Shopsは公式APIという明確な境界 |
| Torima等の多販路ツール | 複数販路、在庫連動 | 外注工程、証憑、税務境界の説明が弱い場合がある | 現物作業と承認・監査・証憑を一つの履歴へ統合 |
| メルカリShops公式API | 公式、商品・在庫・注文・発送を連携可能 | 契約と導入が必要 | Sandboxから安全に導入し、現場アプリと業務データへ接続 |

## 提供価値と差別化の仮説

1. 1商品1記録: SKU、写真、採寸、状態、仕入れ証憑、出品候補、販売、配送、利益を同じIDで追える。
2. 現物に強いiPhone: 撮影順、採寸図、音声入力、OCR、撮り忘れ警告を片手で使える。
3. 規約準拠の二層連携: 個人版は手動引き渡し、Shopsは契約済み公式API。
4. 外注に強い承認: 最小権限、担当、期限、差戻し、監査ログ。
5. 税務AIを越境させない: 証憑と計算の根拠を整え、判断は本人または税理士へ戻す。
6. Notionを捨てない: MVPでは既存Notionへ必要最小限を同期し、移行リスクを下げる。

## 予備MVP

### 入れる

- iOS: 商品コード発行、写真撮影、撮影チェック、採寸入力、音声・OCR補助、状態入力、途中保存
- 共通: AI商品名・説明文候補、文字数と禁止表現チェック、人による確認・差戻し
- 写真: 既存の安全な正方形化、白余白、ブランド・サイズ表示、元写真保護
- Web: 商品一覧、右側詳細、工程状態、不足・確認待ち、担当、検索、承認
- 出品引き渡し: 個人版用の文章コピー、写真一括ダウンロード、公式画面を開く、完了記録
- Shops: Sandbox上の非公開商品作成と承認フローのモック
- 在庫・配送: 棚番、販売済み、梱包、発送、受取評価待ち
- 収益・帳簿資料: 仕入れ、売価、手数料、送料、粗利、証憑添付、仕訳候補、CSV
- 外注: 撮影者・検品者・承認者・発送者・経理の役割、監査ログ
- Notion: 既存DBとの一方向または明示的な同期、競合時は自動上書きしない

### 入れない

- 個人版メルカリの自動出品、下書き自動保存、一括値下げ、自動コメント、自動再出品、自動取引
- ログインCookie、パスワード、SMS認証番号の取得・共有
- 非公開API、通信模倣、検知回避、ランダム待機
- 契約前のメルカリShops本番書き込み
- AIによる税務相談、税区分の最終判断、確定申告書の作成・提出
- LiDAR等による自動採寸の確定値化。端末差と誤差検証が必要なため、最初は手入力と画像補助にする
- 複数販路のリアルタイム在庫連動
- 本番公開、課金開始、PRマージ
