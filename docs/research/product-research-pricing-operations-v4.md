# 商品リサーチ・価格運用の再調査 v4

確認日: 2026-08-13（JST）  
対象: 仕入れ → 検品の商品同定・相場確認、値下げ・セール運用  
状態: 追加モック4枚をSlackへ提出済み、承認待ち。Notion仕様化・Goal・実装は未開始。

## 結論

1. 商品リサーチは、iPhoneでバーコード・タグ・型番・商品写真を読み取り、検索語と比較条件を作るところまで自動化する。相場データは、利用者が各販売チャネルの公式検索で確認し、比較対象を選んで保存する。公開されていない検索APIの推測利用、画面スクレイピング、ログイン情報の代理利用は行わない。
2. 比較結果は「販売中の希望価格」と「売却済みとして観測できた価格」を分ける。件数 `n`、取得日時、状態、送料負担、完全一致か類似品か、除外理由を残し、AIが価格を自動確定しない。
3. 個人向けメルカリの価格変更は、当アプリで下書き・利益確認・承認・作業待ち一覧を作り、本人がメルカリ公式アプリまたはWebで変更して確認する。非公式API、Cookie、SMS、RPA（画面をロボット操作する仕組み）は使わない。
4. メルカリShopsは、MVPでは管理画面から取得した商品データを基に、商品IDと変更項目を含む公式形式の更新CSVによる価格変更を採用する。タイムセールとクーポンは公式管理画面へ手動で引き渡す。APIは契約、書面承認、現行スキーマで価格変更に対応することが確認できた後だけ追加する。
5. 「毎日○円ずつ」「○%OFF」は内部の運用計画として管理できる。ただし、個人向けメルカリへ無人で連続反映する機能にはしない。期日ごとに担当者が公式画面で実施し、結果を確認して監査ログへ残す。
6. メルカリShopsでは、公式タイムセール利用時を除き、商品名・説明・画像に「値引き」「セール」、値引率・値引額、値引前価格を記載できない。当アプリはこれらを自動生成せず、検出時は承認とCSV出力を停止する。

## 1. 仕入れ → 検品の商品リサーチ

### 1.1 公式に確認できたこと

- Apple VisionKit の `DataScannerViewController` は、カメラ映像から文字と機械可読コード（バーコード等）を読み取れる。対応端末かを `isSupported`、現在利用できるかを `isAvailable` で確認し、カメラ用途説明と利用者の許可が必要である。Visionの文字認識は端末内で実行でき、候補、信頼度、位置を取得できる。
- JAN標準はGTIN-13、短縮JANはGTIN-8、UPCはGTIN-12である。番号は事業者と商品を識別するキーであり、中古品の状態、真正性、販売相場は含まない。
- Google ML KitにもiOS向けのバーコード読取と日本語OCRの公式SDKがあり、Apple純正だけで要件を満たせない場合の候補となる。
- メルカリ公式検索は、キーワード、撮影した写真、アルバム画像、商品ページ画像による検索と、絞り込み・並べ替えを提供する。検索条件は最大100件まで保存できる。
- メルカリ公式は、販売価格を決める際に、同じ商品の状態、送料負担、配送条件等をそろえて類似商品を比較するよう案内している。iOSの出品ホームには「相場を調べる」導線がある。
- GS1 の Verified by GS1 は GTIN（JAN等の商品識別番号）から会社・商品情報を確認できるが、一般公開Webは1日30回までで、公開APIは提供されていない。自動照会やスクレイピングには使わない。
- Google Cloud VisionのWeb Detectionは、Webエンティティ、同一・類似画像、掲載ページURLを候補として返せる。ただし商品同定や相場確定を保証せず、画像を外部クラウドへ送る明示同意が必要である。Product Searchは自社で登録した商品カタログとの類似検索で、Google Lensの公開Web商品データベースではない。

### 1.2 MVPの安全な流れ

1. 仕入れ受付で商品を仮SKU（商品ごとの管理番号）にひも付ける。
2. iPhoneでJAN/GTIN、品質表示タグ、ブランドタグ、型番、商品全体を撮影する。
3. 原則として端末内OCR（画像の文字読み取り）と画像比較が、ブランド、型番、ライン、色、素材、表記サイズ、カテゴリの候補を出す。外部クラウド画像検索は有料版の任意機能とし、送信前に同意を得る。
4. 人が候補を確認する。AI候補は正本を上書きせず、確定者・確定日時を残す。
5. アプリが検索語パックを作る。例: `ブランド + 型番 + 色 + サイズ + カテゴリ`。
6. 利用者が公式検索を開き、状態、送料負担、サイズ、公開状態をそろえて比較対象を選ぶ。
7. iOSの共有機能で根拠URLを当アプリへ戻す。共有できない場合はURL貼付と手入力を使い、アプリが外部ページを自動巡回しない。
8. 比較データを構造化して保存し、中央値、四分位範囲、最小・最大、件数、信頼度を表示する。
9. 検品結果と不一致なら「再確認」に戻す。真正品判定や仕入可否をAIだけで確定しない。

### 1.3 比較証拠として保存する項目

- `source_channel`, `source_url`, `captured_at`
- 検索語、絞り込み条件、並べ替え条件
- 販売中 / 売却済みとして観測 / 状態不明
- 表示価格、送料負担、商品状態
- ブランド、型番、色、サイズ、カテゴリ
- 完全一致 / 同系統 / 類似品
- 採用 / 除外、除外理由
- 入力者、確認者、確認日時

第三者の商品画像を自社の出品画像として再利用しない。スクリーンショットを証拠保存する場合は非公開・期限付きとし、保持期間と権利確認を別途定める。Notionには第三者画像や個人情報を同期しない。

### 1.4 表示ルール

- 販売中は「希望価格」、売却済みは「観測価格」と表示し、混ぜない。
- 完全一致がない場合は「同系統の参考値」と明示し、信頼度を下げる。
- 比較対象3件未満は「根拠不足」、3〜4件は「データ少」、5件以上でも状態差を人が確認する。施策比較の `n < 10` は「参考値」と表示する。いずれも公式基準ではなく本アプリの初期品質ルールであり、実データ検証後に見直す。
- 中央値だけでなく範囲・除外件数・取得日時を表示する。
- AIは「価格候補」「確認候補」までとし、「適正価格」「必ず売れる」「真正品」と断定しない。

### 1.5 未確認

- 個人向けメルカリの商品検索・売却価格を第三者アプリから取得できる一般公開APIは確認できていない。
- Google Lensを第三者iOS/Webアプリから公開Web商品検索として呼び出す一般公開APIは確認できていない。
- Mercari Shops APIは自店の商品・在庫・受注管理向けであり、第三者商品の販売済み相場を取得する用途は確認できていない。
- 各チャネルの検索結果URL、売却済み表示、画像検索の外部アプリ連携可否は変更され得るため、実装時に再確認する。

## 2. 値下げ・セール運用

### 2.1 公式に確認できたこと

#### 個人向けメルカリ

- 売れる前の商品は公式アプリ/Webの商品編集画面で価格変更できる。売却後は変更できず、オークション形式は入札後に変更できない。
- 購入希望価格のリクエストは、出品者が承諾して価格変更する仕組みで、購入を保証しない。メルカリShopsは対象外。
- 以前の「まとめて値下げ」機能は2024-08-22に提供終了している。現行機能として設計しない。
- メルカリが選定するSALE/クーポンは、出品者が自由に設定する一般機能ではなく、購入者向け表示と出品者利益への影響も別扱いである。
- 商品プロモーションは公式アプリで単品または同時最大100件まで設定でき、本人確認が必要。期間中に売れた場合は購入時販売価格の5%がプロモーション利用料として発生し、通常の販売手数料とは分けて記録する。期間は40日以内で、一度開始すると出品を公開停止する場合を除き停止できず、再公開すると再開する。

#### メルカリShops

- PC版管理画面では、公式CSVで一度に最大10,000商品を変更できる。現在の商品データをダウンロードし、商品IDと変更項目を含む公式形式の更新CSVを作る。変更しない項目は省略できるが、商品IDやSKU編集時のSKU ID等、公式が指定する必須・編集不可IDは出力値を保持する。1,000件超では公式プレビューが先頭1,000件に限られるため、対象ID、件数、変更前後集計を当アプリ側でも照合する。
- CSVで設定できる販売価格は300円〜9,999,999円。タイムセール設定中または予約を含む商品は、その間CSVで価格変更できない。
- 公式タイムセールは1〜90%OFF、割引後300円以上かつ現在価格より100円以上安いこと、開始は30日以内、期間は最長30日等の条件がある。開始後に変更できない項目があるため、公開前プレビューが必要。
- タイムセールは、(a)過去8週間のうち合計4週間の同一価格実績、または販売期間が8週間未満なら過半かつ2週間以上の同一価格実績があり、さらに直近2週間にも同価格実績がある商品、もしくは、(b)過去45日間のうち累計30日以上の販売実績がある商品が対象となる。公式側は実績から「値引き前価格（同一価格）」または「過去価格（中央値）」を自動算定し、利用者は編集できない。現在価格と異なる場合もあるため、出力直前に対象可否と算定価格を公式画面または公式CSVで再確認する。
- 公式タイムセール利用時を除き、商品名・説明・画像に「値引き」「セール」、値引率・値引額、値引前価格を記載できない。根拠があるか否かにかかわらず、当アプリは検出時に承認とCSV出力を停止する。

### 2.3 価格データと計算

全金額は通貨と税込・税抜の基準を保持し、同じ計算内で混在させない。メルカリShopsの公開価格は総額表示として保存し、会計照合用の税区分・税抜換算は別フィールドで管理する。

- 初回公開価格 `P0`: 内部履歴。自動で「通常価格」にしない。
- 現在の基準販売価格 `Pt`: タイムセール等を除く現在の公開価格。
- 公式比較対照価格 `Pc`: 公式タイムセール画面またはCSVが販売実績から自動算定した編集不可の値引前価格。`P0` や `Pt` で代用しない。
- 注文時商品価格 `Ps`: 注文時に固定した、クーポン適用前の商品価格。送料は別フィールドで持つ。
- 販売者負担割引 `Ds`: 値下げ・ショップクーポン等、販売者収入を減らす確定額。
- チャネル負担クーポン `Dc`: 買い手価格を下げるが、販売者負担ではない確定額。
- 買い手商品支払額（商品分）: `Ps - Ds - Dc`。
- 販売者の商品収入（精算前推計）: `Ps - Ds`。`Dc` は控除せず、補填額を別加算して二重計上しない。
- 販売者の商品収入（確定・返金前）: 注文明細または精算明細で確定した、販売者負担割引後、かつ返金・販売手数料・プロモーション利用料・送料その他控除前の商品代金。振込額や控除後の手取り額を使わない。

Shopsが発行するショップクーポンは `Ds`、プラットフォーム側が負担するクーポンは `Dc` として別種別で保存し、相互に置き換えない。標準価格の変更や公式タイムセール後の注文価格が `Ps` に既に反映される場合は、同じ値下げ額を `Ds` として再控除しない。チャネルごとの割引配賦規則を版管理する。

負担者または精算結果が未確認の場合は0円とせず「未確認」とし、取引貢献利益を確定しない。キャンセル、返品受付、商品受領、返金成功、在庫復帰は別イベントとして記録する。

- 正味商品売上 = 販売者の商品収入（確定・返金前） - 別イベントとして成功した返金の販売者負担分。取得元が返金控除後の場合は返金前金額へ復元してから計算し、同じ返金を再控除しない。
- 純売上原価 = 販売済み原価 - 再販可能として在庫へ戻した返品原価
- 商品粗利益 = 正味商品売上 - 純売上原価
- 取引貢献利益 = 商品粗利益 - 実販売手数料 - 実プロモーション利用料 - 出品者負担送料 - 梱包費 - 返品直接費

返金申請中は成功済み返金へ含めない。再販不可品は、人が在庫調整を承認するまで原価を自動で戻さない。全画面に「運用分析の参考値です。会計上の利益・所得・税額ではありません」を固定表示し、税務判断は本人または税理士が行う。

### 2.4 価格下限と承認停止

`C = 商品原価 + 固定送料 + 梱包費 + 固定手数料`、目標貢献利益を `T`、販売手数料率を `r` とする。手数料が値引後商品価格に掛かる単純な場合、販売者負担の固定額割引 `D` に対する最低公開価格は `ceil(D + (C + T) / (1 - r))`、割合割引 `d` に対しては `ceil((C + T) / ((1 - d) × (1 - r)))` とする。公開価格自体を変更し、追加の販売者負担割引がない場合は `D = 0`, `d = 0` とする。

全入力は同じ税込・税抜基準に統一する。最低手数料、段階送料、異なる手数料基準を持つチャネルでは単純式を使わず、公式ルールに基づいて候補価格を刻みごとにシミュレーションする。次の場合は自動承認せず停止する。

- 原価、送料、手数料、クーポン負担が未確認
- 方針上の価格下限未満
- 取引貢献利益がマイナス
- 在庫0、販売済み、入札後、タイムセール中/予約中
- 同じ商品が別キャンペーンに重複
- 大幅値下げまたは一括変更で承認者が未設定
- メルカリShopsの公式タイムセール利用時以外に、商品名・説明・画像へ「値引き」「セール」、値引率・値引額、値引前価格を含む

### 2.5 運用フローと監査

1. キャンペーン下書き
2. 対象SKU・期間・基準価格の根拠を固定
3. 買い手支払、販売者入金、手数料、送料、粗利益、取引貢献利益をプレビュー
4. 担当者が提出し、権限を持つ承認者が承認/差戻し
5. チャネルごとの公式経路へ引き渡し
6. 公式側で反映を確認
7. 変更前後、実行者、承認者、理由、証拠、成功/失敗を追記型の監査ログに保存

履歴は上書きせず、誰がいつ何を変更したかを残す。

### 2.6 効果確認

- 7日・14日・30日販売率 = 各期限までに取引完了し、その集計時点で返品確定していないSKU数 ÷ キャンペーン開始時の対象SKU数
- キャンセルは販売数に含めない。後日返品が確定した場合は、集計基準日と改訂履歴を残して販売数を戻す。
- 開始後に追加・除外したSKUは元の群に残し、変更理由を記録する。追加分は別コホート（同じ開始条件の集団）として表示する。
- 売切日数中央値は販売済みSKUだけで計算し、未販売SKUを0日として扱わない。未販売分は在庫年齢帯を併記する。
- 販売者負担割引率、商品粗利益、取引貢献利益、返品率、期末未販売在庫を併記する。

比較群は開始日、チャネル、カテゴリ、状態、価格帯、在庫年齢、送料条件、季節、観測期間をそろえる。無作為割付でない比較は「観測上の傾向」と表示し、「値下げにより売れた」等の因果効果や最適価格を断定しない。`n < 10`、欠損、返品観測期間未了は参考値とし、断定的なAI提案を出さない。

### 2.7 未確認

- メルカリShops APIで価格変更、タイムセール、クーポンを操作できる範囲と契約条件
- 各チャネルで取得できる価格履歴、クーポン負担、手数料返還、返金確定時点
- 個人向けメルカリの商品プロモーションの一括設定上限や手数料条件の将来変更

API対応は、契約・書面承認・現行API仕様・Sandboxでの検証がそろうまで「未対応」と表示する。

## 3. 外注に対応する権限

- 撮影・検品担当: 写真、タグ、採寸、商品候補の入力のみ
- リサーチ担当: 公式検索、比較候補の採用/除外と根拠入力
- 価格担当: キャンペーン下書きのみ
- 承認者: 価格下限違反、大幅変更、一括変更の承認
- 実行者: 公式管理画面での反映と結果確認
- 経理担当: 精算・返金・費用照合のみ

個人向けメルカリアカウントのID、パスワード、Cookie、SMS認証を外注担当へ共有しない。住所・本人情報は役割と期間を限定して表示する。

## 4. 無料版と有料版

無料版:

- 単品のバーコード/OCR読み取りと人の確認
- 検索語パックと公式検索への手動引き渡し
- 比較対象の手入力、基本中央値・範囲
- 単品の価格履歴、値下げ下書き、費用プレビュー
- 根拠不足・赤字・価格表示ルールの警告
- 基本監査ログ

有料版:

- 一括リサーチ作業台、比較証拠の履歴・出力
- AIによる商品同定候補と異常検知
- チーム権限、担当割当、二段階承認
- 一括キャンペーン、Shops公式CSV生成・結果照合
- 契約済み公式API連携
- 価格下限ルール、仕入先/カテゴリ別テンプレート
- コホート比較、精算・会計照合、監査ログ出力

安全警告、人の最終確認、監査の最低限は無料版でも削らない。

## 6. 追加モックの確認条件

- 商品候補はAIではなく人が確定する。
- 公式検索で比較対象を人が選ぶことが見える。
- 販売中希望価格と売却済み観測価格が分離される。
- 件数、取得日、商品状態、送料負担、採用/除外理由が確認できる。
- 個人向けは手動公式操作、Shopsは公式CSV/公式管理画面と分かる。
- ○円値下げ・○%値下げ・公式タイムセールの下書き、利益確認、承認、結果確認が一続きで見える。
- Shops公式タイムセール外の禁止価格表示、価格下限割れ、欠損データを止める。
- 外注担当・承認者・実行者の分離と監査ログが見える。
- 非公式API、スクレイピング、Cookie共有、無人RPAを前提にしない。
