# 在庫ロケーション管理 調査・設計 v1

- 確認日: 2026-08-14（JST）
- 状態: UI承認前の調査正本
- 対象: 中古衣料を中心とした1点物在庫、iPhone現場作業、PC管理、外注対応

## 結論

MVPでは、各商品個体へ変更しない自社在庫番号を付け、`商品QR → 保管場所QR → 人が内容確認`の順で格納・移動・ピッキングを確定する。

保管場所は `拠点 → 部屋 → ゾーン → 棚／ハンガーラック → 段 → 箱／位置` の階層で管理する。棚や段は固定場所、箱・衣装ケースは移動可能な容器として分ける。各部屋と正確な棚位置には案内写真を持たせる。

GS1の識別コードを無断で発番せず、MVPは通常のQRと必要に応じてCode 128を使用する。古物台帳、原価、購入者情報はロケーション情報と分離する。

## 現状の不足

既存M05は注文、ピッキング、梱包、発送、簡易棚卸を一枚で扱い、既存W01はSKU一覧へ棚番を表示している。しかし次が専用設計されていない。

- 拠点・部屋・ゾーン・棚・段・箱・ハンガー位置の階層
- 部屋入口の案内写真と、商品を探すための棚／段／箱写真
- SKUと別の、現物ラベル用の変更しない在庫管理番号
- 商品ラベルと場所ラベルの二重読取
- 入庫、格納、移動、ピッキング、返品隔離、棚卸を通した場所履歴
- 誤棚、未発見、予定外発見、ラベル破損、容量超過の例外処理
- 在庫責任者、格納担当、棚卸担当、発送担当の権限差
- 箱を移動したときの中身全件の有効位置

この不足はM05/W01への小さな追記では解消せず、専用のモバイル画面M12とWeb画面W10が必要である。

## 一次情報で確認できた事実

### GS1と識別コード

- GTINは商品、GLNは組織・場所、SSCCは物流単位を識別する。GS1識別コードの発番にはGS1事業者コードが必要である。
  - https://www.gs1.org/standards/id-keys
  - https://www.gs1jp.org/standard/identify/
- GLNは倉庫などの物理的な場所にも設定できるが、社内の棚別コードとは目的が異なる。GS1 Japanも、社内コードと企業間取引用コードを分け、棚別GLNは変更連絡が煩雑になる点を案内している。
  - https://www.gs1jp.org/standard/identify/gln/
  - https://www.gs1jp.org/standard/identify/gln/allocate_location.html
- SSCCはケース、パレット、荷物などの物流単位を識別する18桁番号である。
  - https://www.gs1jp.org/standard/identify/sscc/
- GTINだけでは同じ型の複数個体を区別しない。
  - https://www.gs1.org/standards/gs1-system-architecture-document/current-standard

### iPhoneでの読取と写真

- Appleの`DataScannerViewController`は、カメラ映像中のQRなどの機械可読コードを読み取れる。利用前に端末対応状況、利用可能状態、カメラ許可を確認する必要がある。
  - https://developer.apple.com/documentation/visionkit/datascannerviewcontroller
  - https://developer.apple.com/documentation/visionkit/scanning-data-with-the-camera
- AVFoundationはQR、Code 128、EAN-13、Data Matrix等の読取に対応する。
  - https://developer.apple.com/documentation/avfoundation/machine-readable-object-types
- 写真にはGPSなどの位置情報が含まれる場合があり、共有時に参照され得る。
  - https://support.apple.com/guide/personal-safety/manage-location-metadata-in-photos-ips0d7a5df82/web
- PhotosPickerは利用者が選んだ写真だけをアプリへ渡す仕組みで、写真ライブラリ全体の許可を不要にできる。
  - https://developer.apple.com/documentation/swiftui/view/photospicker%28ispresented%3Aselection%3Amaxselectioncount%3Aselectionbehavior%3Amatching%3Apreferreditemencoding%3A%29

### 棚卸と法定記録

- 国税庁の個人事業者向け資料は、棚卸表に種類・品質・型ごとの数量と金額を記載し、実地棚卸のメモも保存するよう案内している。棚卸表等の保存期間は5年と案内されている。
  - https://www.nta.go.jp/taxes/shiraberu/shinkoku/kojin_jigyo/0021012-127_01.pdf
  - https://www.nta.go.jp/taxes/shiraberu/shinkoku/kojin_jigyo/index.htm
- 古物営業法の対象取引では、取引日、品目・数量、特徴、相手方情報、本人確認方法等の記録が必要となる。電子記録には保存と営業所での表示要件がある。
  - https://laws.e-gov.go.jp/law/324AC0000000108
  - https://www.keishicho.metro.tokyo.lg.jp/tetsuzuki/kobutsu/youshiki/chobo_yoshiki.html

保管場所・棚番号は、これらの法令で列挙された法定項目ではなく、業務上追加する情報である。本アプリのロケーション履歴を古物台帳や税務上の棚卸表そのものとは表示しない。

## 製品設計上の判断

以下は一次情報を踏まえた本製品の設計判断であり、法令やGS1の必須仕様ではない。

### 識別子

- `ProductSKU`: 商品データを工程全体で結ぶ不変ID。
- `InventoryUnit`: 現物1点を表す個体。中古1点物では原則としてSKUと1対1。
- `inventory_number`: `INV-000123`のように人が読める変更しない管理番号。
- `label_token`: QRへ格納する推測困難な内部トークン。種類、内部ID、版、チェック値だけを含める。
- `external_gtin`: JAN/EAN/UPC等のメーカー商品コード。参考属性であり、現物個体の識別には使わない。

ラベルにはQRと人が読める管理番号を併記し、必要な現場だけCode 128も併記する。住所、氏名、原価、利益、購入者情報、認証用秘密情報をQRへ入れない。QRを読めること自体を閲覧権限にせず、サーバーで担当範囲を確認する。

### 場所階層

`Site → Room → Zone → Rack/Rail → Level → Bin/Slot`

- `Site`: 自宅保管、事務所、外部倉庫などの拠点。MVPは1拠点でもデータ構造は階層対応する。
- `Room`: 洋室A、作業部屋、保管室など。
- `Zone`: 北側、入口右、撮影待ち、返品隔離など。
- `Rack/Rail`: 棚A、ハンガーラックH1など。
- `Level`: 上段、中段、下段など。
- `Bin/Slot`: 衣装ケース、箱、個別位置など。
- `Container`: 箱やカゴなど移動する容器。固定場所ノードとは別管理し、現在位置を持つ。

場所コード例は `RM-A / Z-N / R03 / L02 / BX-014` とし、画面には `自宅保管 > 洋室A > 北側 > 棚03 > 2段目 > 箱014` のようなパンくずを表示する。

### 写真

- 部屋写真: 入口から見た全景と、進行方向の目印。
- 棚写真: 棚・ラック全体と表示コードが同時に見える写真。
- 正確位置写真: 段、箱、ハンガー位置の近接写真。
- 写真には撮影者、撮影日時、ハッシュ、対象場所、版、GPS除去済み状態を持たせる。
- 外部表示用の派生画像は位置EXIFを除去する。人物、表札、配送伝票、鍵、暗証設備が写る場合は公開せず差し戻す。
- 場所写真はNotionへ送らず、非公開Storage（クラウド上の保管庫）で役割別に表示する。

### 主要データ

- `LocationNode`: 親、種類、コード、名称、稼働状態、容量方針、写真、最終棚卸日。
- `Container`: 箱番号、現在位置、容量、状態、中身件数、ラベル版。
- `InventoryUnit`: 在庫番号、SKU、現在の固定場所または箱、業務状態、例外状態。
- `MovementEvent`: 移動元・先、理由、実行者、承認者、商品・場所の読取証拠、端末時刻、サーバー時刻、取消元。
- `CountSession`: 対象範囲、開始時点、担当、読取結果、差異、再棚卸、承認。
- `LocationPhoto`: 場所、版、撮影者、日時、ファイルハッシュ、GPS除去、閲覧区分。
- `AccessAssignment`: 担当者、許可する場所の枝、作業種類、開始・終了時刻。
- `LegalLedgerLink`: 古物台帳レコードへの参照だけ。相手方個人情報を場所レコードへ複製しない。

### 状態

- 業務: `入庫待ち → 未格納 → 在庫中 → 引当済み → ピッキング済み → 梱包済み → 発送済み`
- 返品: `返品到着 → 隔離 → 検品 → 再格納／廃棄候補`
- 棚卸例外: `正常／未発見候補／誤棚／予定外発見／ラベル重複／読取不能／紛失確定`
- 場所: `使用中／一時停止／廃止`

誤棚を見つけても現在位置を自動上書きしない。`元へ戻す`または`発見場所へ変更`を理由付きで選択する。紛失確定、廃棄、数量減少は在庫責任者またはオーナーの承認を必須にする。

## 標準フロー

### 入庫・格納

1. 商品ラベルを発行し、`未格納`にする。
2. 商品QRを読む。
3. 格納先QRを読む。
4. 同一workspace、場所の使用状態、担当権限、容量を検査する。
5. 商品、場所、写真、状態を確認し、人が`格納を確定`する。
6. 移動イベントと現在位置を一つのDB処理で更新する。

### 移動

1. 商品または箱を読む。
2. 移動元を照合し、移動先を読む。
3. 理由を選び、人が確定する。
4. 箱移動では箱と中身全件の有効位置を同じ移動グループで追跡する。

### ピッキング

1. 担当注文を開く。
2. 部屋、棚、段のパンくずと位置写真で現物を探す。
3. 商品QRを読み、予定商品と照合する。
4. 場所QRを読み、予定場所と照合する。
5. 一致時だけピッキング済みへ進める。不一致は例外へ送る。

### 返品

返品は必ず隔離場所へ入れ、状態確認後だけ再格納する。人の検品なしで販売可能へ戻さない。

### 棚卸

1. 棚・段・箱QRを先に読む。
2. その場所にある商品を連続スキャンする。
3. 開始時点の期待在庫と移動イベント番号を固定する。
4. `一致／未読取／予定外／別棚予定／二重読取`へ分類する。
5. 未発見は別担当者が再確認するまで`紛失確定`にしない。
6. 解決理由、担当者、承認者、元データを残す。

通信不能時はMVPで移動を確定せず`同期待ち`にする。再送では同じ操作を二重登録しない冪等キー（同じ操作を一度だけ有効にする識別子）を使う。

## 役割と最小権限

| 役割 | 主な作業 | 禁止・非表示 |
|---|---|---|
| オーナー | 紛失・廃棄・数量調整の最終承認、全体確認 | なし。ただし重要操作は再確認 |
| 在庫責任者 | 場所作成、写真承認、ラベル管理、差異解決、棚卸完了 | 古物・税務の無確認確定 |
| 格納・移動担当 | 割当商品の格納、移動候補、場所写真候補 | 場所階層変更、ラベル無効化、数量調整 |
| 棚卸担当 | 割当場所のブラインド棚卸、差異報告 | 期待数量の事前閲覧、差異の自己確定 |
| 発送担当 | 担当注文の場所案内、ピッキング、梱包 | 原価、利益、全在庫、古物台帳、税務 |

外注者には割り当てた商品、作業、場所の枝だけを期限付きで表示する。発送先住所は必要な注文と時間に限り、閲覧履歴を残す。

## P0とP1

### P0

- 商品個体の在庫番号、QR、目視コード
- `拠点 → 部屋 → ゾーン → 棚／ラック → 段 → 箱／位置`
- 部屋全景、棚全景、正確位置の写真
- 商品→場所の二重読取による格納・移動・ピッキング
- 未格納、在庫中、引当、ピッキング、返品隔離の基本状態
- 在庫責任者、格納担当、棚卸担当、発送担当の最小権限
- 場所単位の棚卸と、未発見・誤棚・予定外発見の差異キュー
- QR非対応・カメラ拒否時の管理番号手入力
- 追記型移動履歴、監査、オフライン同期待ち

### P1

- 箱移動に伴う中身全件の一括有効位置
- ラベルプリンター専用連携、印刷テンプレート管理
- 複数拠点間の移送と受渡し承認
- 定期循環棚卸、動的な担当割当、最短ピッキング順
- 容量・混載・商品属性による格納先候補
- フロアマップ、BLE/RFID、GS1 GLN/SSCC/GRAI連携

P0でも箱は場所として登録できるが、箱だけを動かして中身全件を連動させる高度な処理はP1とする。

## 専用UI案

### M12 在庫・ロケーション作業

1. 在庫担当ホーム: 今日の格納、移動、棚卸、例外、担当範囲。
2. 商品読取: 在庫番号と商品写真を照合。
3. 場所読取: パンくず、部屋写真、棚／段写真を表示。
4. 格納確認: 商品と場所を並べ、人が確定。
5. 移動: 移動元、移動先、理由、同期待ち。
6. ピッキング: 経路、位置写真、商品＋場所の一致確認。
7. 棚卸差異: 予定場所と発見場所、未発見、再確認依頼。

### W10 在庫ロケーション管制

- 左: 場所ツリー、状態、容量、最終棚卸。
- 中央: 選択場所の全景／正確位置写真、保管中の商品一覧。
- 右: 在庫責任者、担当範囲、例外、承認待ち。
- 詳細: 在庫番号、SKU、現在地、業務状態、移動タイムライン。
- 作業: 場所登録、ラベル印刷、移動履歴、棚卸セッション、外注割当。

## 受け入れ条件候補

- INV-AC01: 在庫中の商品は、有効な固定場所または箱を1つだけ持つ。場所がなければ`未格納`等の明示状態になる。
- INV-AC02: 他workspace、廃止場所、権限外、単品専用場所の容量超過への移動を拒否する。
- INV-AC03: 商品と場所の二重読取が揃わなければ、格納、移動、ピッキングを確定しない。
- INV-AC04: 通信再送や同時操作でも同じ移動イベントを二重作成しない。
- INV-AC05: 場所写真の外部表示用派生画像から位置EXIFが0件で、権限外利用者は取得できない。
- INV-AC06: 外注者は割当範囲外の商品、場所、原価、個人情報、古物台帳、税務情報を取得できない。
- INV-AC07: 誤棚・未発見は現在位置を自動上書きせず、予定場所、発見場所、理由、担当、承認を保持する。
- INV-AC08: 紛失確定、廃棄、数量調整は実行者と異なる在庫責任者またはオーナーが承認する。
- INV-AC09: 返品商品は隔離と人の検品なしで販売可能へ戻せない。
- INV-AC10: ラベル再発行後に旧ラベルを読むと警告し、旧版読取を監査へ残す。
- INV-AC11: カメラ拒否、スキャン非対応時も、チェック値付き管理番号の手入力と人の確認で作業できる。
- INV-AC12: 棚卸開始時点、期待対象、全読取、差異、再確認、解決理由を削除せず出力できる。
- INV-AC13: 位置写真に人物、表札、配送伝票、鍵・暗証設備が含まれる場合、公開を止めて差し戻せる。
- INV-AC14: GS1事業者コードと運用契約が未確認の間は、GLN、SSCC、GRAIを生成せず、内部コードと明示する。

- 使用するラベル用紙、プリンター、耐久性、貼付位置
- 倉庫内の通信品質と、オフラインで何件まで作業するか
- 実際の仕入形態ごとの古物台帳・本人確認要件
- 税区分や事業形態ごとの保存要件
