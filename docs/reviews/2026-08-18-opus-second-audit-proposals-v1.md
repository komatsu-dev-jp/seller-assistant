## 2. 推奨案の詳細

### 2.1 Q1 — 1人運用モード（提案A）

#### 問題の再確認

`AC-050` と `TA-032` は、紛失確定・廃棄・数量調整に「異なる2人の人間」を必須にしている（`requester_id != approver_id`、`distinct human actor >= 2` を100%検証）。一方 `docs/specs/mvp-product-spec-v1.md:308` のプラン表では Free と Solo Pro のメンバーは1人。役割を持ち替えても `distinct human actor >= 2` は満たせない。

結果、1人のユーザーは棚卸を実行できても差異を解決できず、商品を破損しても廃棄を記録できない。在庫数と期末棚卸高がずれ続け、会計出力が恒久的に不正確になる。会計CSVは Free でも提供する前提（同ファイル:307）。

#### 推奨する設計

2人目を要求する代わりに、**時間を空けた本人の再確認**で代替する。安全側の意図（思い込みと即断を防ぐ）を保ったまま、1人でも在庫と会計を閉じられるようにする。

**適用条件（設定で緩められないようにする）**

- `solo_mode` はワークスペース設定ではなく、**有効メンバーが1人である期間に自動適用される判定**とする。人が任意にONにできる設定にすると安全性が下がる
- 有効メンバーが2人以上になった時点で、以降の新規確定は `dual_actor` を必須に戻す

**再確認の成立条件（すべて必須）**

1. 初回の差異報告・廃棄申請から **24時間以上** 経過している
2. 初回とは **別のセッション** で実行される
3. 証拠写真を **1枚以上** 添付する
4. 理由コードを選択し、自由記述の理由を入力する

**記録**

- `inventory_discrepancy` と `audit_event` に `verification_mode` を持たせ、`dual_actor` / `single_actor_delayed` を区別する
- 月次集計と会計出力に、`single_actor_delayed` で確定した件数と金額を**併記する**（隠さない）

**受け入れ条件の書き換え案**

- `AC-050` を次の趣旨へ改訂する。「未発見候補、紛失確定、廃棄、数量調整は、有効メンバーが2人以上のワークスペースでは依頼者と承認者が異なることを必須とする。有効メンバーが1人の期間は、24時間以上経過した別セッションでの再確認、証拠写真、理由入力を必須とし、`verification_mode=single_actor_delayed` として監査へ残す。いずれの場合も即時の単独確定を拒否する」
- `TA-032` の `distinct human actor >= 2` を、`verification_mode` に応じた分岐条件へ改める。`single_actor_delayed` では「初回と再確認の時刻差 >= 24時間」「session_id が異なる」「証拠 >= 1件」をDB制約またはdomain testで検証する

**プラン表の修正**

`docs/specs/mvp-product-spec-v1.md:306` の在庫ロケーション行を改める。Free / Solo Pro に「差異解決（単独・時間差再確認）」を追加し、Team は「差異承認（2人確認）」とする。現状は Free に「棚卸」がありながら差異解決手段がなく、行き止まりになっている。

#### 代替案（採らなかった理由も記す）

- **Solo Pro を対象外にして最小2人からにする**: 実装は単純になるが、想定ユーザー（1人で運用する物販事業者）を製品から外すことになる。第2章の対象ユーザー表と矛盾する
- **1人のときだけ2人確認を免除する**: 監査の一貫性が失われ、「1人だから確認なしで確定できる」という最も危険な状態になる

### 2.2 Q3 — P0を2段に分割する（提案D）

#### 根拠

現在のP0必須ACは55件中38件（69%）。除外は17件のみ。「まず動かす薄い一本」と呼びながら、実質は製品のほぼ全体である。さらに仕様書全体で工数・期間の記載が1箇所もない。

#### 推奨する分割

**P0-α（仕入から会計まで一本を通す）**

試験SKU 1点について、仕入証憑 → SKU発行 → 在庫番号発行 → 場所写真付き格納 → 撮影・採寸 → AI文章候補 → 本人による出品引渡し → 手入力注文 → 商品＋場所の二重読取 → 発送 → 収益事実 → 仕訳候補 → 会計CSV。

対象AC: `AC-001`、`003`〜`008`、`013`〜`014`、`018`〜`019`、`021`〜`023`、`025`〜`026`、`028`〜`034`、`039`、`042`〜`048`、`052`〜`055`（35件）

`AC-039`（旧実装移植の秘密0件）は現行ではP1扱いだが、`docs/DECISIONS.md:85` が移植の適用範囲を「Goal初期実装」と定めているため、P0-αへ移す（指摘M4）。

**P0-β（例外と差異の処理）**

棚卸差異、返品隔離、それらの解決フロー。

対象AC: `AC-020`、`049`、`050`、`051`（4件）

#### この分割の効果

- H1の2人確認問題が P0-α の外に出る。αの実装中にQ1の結論を確定させればよい
- αだけで「仕入れた物が売れて記帳される」一本が通るため、縦導線の検証という目的は保てる
- ただし α も35件で決して小さくない。財務・監査・権限のACは削れないため、これが本プロジェクトの実際の規模である

#### 停止条件の書き換え案

現行の「P0が未完成のままP1へ進まない」を、次の3段へ改める。

1. P0-α の必須ACが全合格するまで P0-β を開始しない
2. P0-β の必須ACが全合格するまで P1 の機能フラグをONにしない
3. いずれかの段で代表E2E、権限越境、財務fixture、原本・監査保護が失敗した場合は次段へ進まない

## 3. その他の推奨（質問に含めなかったが同時に決めたいもの）

### 3.1 H3 — 計算式を正本へ移す

商品粗利益・取引貢献利益・純売上原価の定義と価格下限の数式が、現在 `docs/research/product-research-pricing-operations-v4.md` にしか存在しない。一方 `docs/specs/mvp-product-spec-v1.md:6` は「内容の正本は `docs/specs/`」と宣言している。

**推奨:** `docs/specs/financial-formulas-v1.md` を新設し、式を移す。式ごとに版番号を振り、`financial_event.rule_version` から特定できるようにする。調査資料からはそちらを参照する向きに逆転させる（現在は仕様書が調査資料を参照している）。

### 3.2 M3 — 効率の受け入れ条件を追加する

現行AC 55件はすべて安全性・正確性・権限・監査に関するもので、人の作業時間に関する条件が1件もない。二重読取・人の確認・承認分離はいずれも安全側に正しいが、確実に作業時間を増やす。増やしてよい上限が決まっていないため、「安全だが手間が増えて使われない」状態でも受け入れ判定は合格してしまう。

**推奨:** 次の趣旨のACを追加する。目標値はユーザーの現在の作業時間を計測してから決める。

- 1商品について、撮影開始から出品準備完了までの実測時間が目標値以内であること
- 50点の一括格納の実測時間が目標値以内であること
- 計測は実機で行い、機種・iOS版・計測者・日時・結果を記録すること

`docs/research/product-discovery.md:235` に「既存在庫10商品で、現状時間と試作品時間を比較する」という計画が既にある。これを受け入れ条件へ昇格させるのが自然。

### 3.3 M1 — 移行専用の軽量経路（提案C）

既存在庫の立ち上げが、MVP範囲・対象外・リスク・ロードマップのいずれにも記載がない。対象外に書かれていないため「やらない」とも読めない。

**推奨:** 写真・採寸・出品文を要求しない最小経路を用意する。在庫番号の発行、ラベル出力、場所の割当、取得原価の一括入力のみ。撮影と採寸は後から追加できる状態にしておく。

これがないと、全在庫を処理し終えるまでアプリと手作業の二重管理になる。実装しないと判断する場合も、対象外へ明記する。

### 3.4 提案F — 調査から仕様への対応表を作る

在庫ロケーションは `INV-AC01`〜`14` が `AC-042`〜`055` へ完全に対応しており、抜けがない。最後に追加された領域だけが正式な引き継ぎを経ているためである。

一方で会計まわりは、`docs/research/integration-decisions-v2.md:126-148` で決めた8種の出力物やCSV分割規則が仕様書へ落ちていない（H2）。調査資料の決定事項と仕様書のACを1対1で並べた表を作れば、同じ取りこぼしを機械的に検出できる。

## 4. 未確認事項（Claude Codeでは決められないもの）

**以下はユーザーの事業に関する事実であり、推測で埋めてはならない。** 判断待ちとして `inbox/` へ立てることを推奨する。

### 4.1 消費税の事業者区分とインボイス登録

`docs/research/integration-decisions-v2.md:130` は「インボイス区分の空欄は『適格』と解釈されるため、未確認のまま空欄出力しない」と決めている。したがって、この設定は**どの区分であっても必ず持つ必要がある**。

**必要な確認事項:**

- 消費税の区分: 免税事業者 / 簡易課税 / 原則課税 のいずれか
- 適格請求書発行事業者（インボイス）の登録有無
- 申告方式: 青色申告 / 白色申告

**推奨する設計（区分の値が確定していなくても進められる部分）:**

- ワークスペース設定へ `tax_scheme`（`exempt` / `simplified` / `standard`）と `invoice_registered`（真偽値）と `filing_method`（`blue` / `white`）を持たせる
- 未設定のまま会計CSV出力を実行できないようにする
- インボイス区分列は、未設定時に空欄で出力せず、出力自体をブロックする

**P0開発中の仮置き値（要確認・実装の前提としてのみ使う）:**

`tax_scheme = exempt`、`invoice_registered = false`、`filing_method = blue`。これは日本の個人事業主で最も多い構成という一般的想定にすぎず、ユーザーの実態を確認したものではない。確認後に変更する前提で使う。

### 4.2 記帳方式

現行仕様は記帳方式（三分法 / 分記法 / 売上原価対立法）を定めていない。これは仕訳候補の構造そのものを決めるため、後から変更すると `journal_candidate` と会計出力アダプタを作り直すことになる。

**推奨（ユーザー確認が取れるまでの案）:** **会計出力は三分法を既定とし、アプリ内部では個別原価を保持する。**

- 根拠: `docs/research/followup-image-measurement-analytics-v3.md:200` が引用する国税庁の手引きでは、売上原価を「期首棚卸高＋年間仕入高－期末棚卸高」で計算する。青色申告決算書の様式もこの形である
- 仕入時に `仕入高` を計上し、期末に棚卸調整を行う
- 内部で保持する個別原価は、`SKU別期末棚卸表` の生成と運用分析（商品粗利益など）に使う
- 運用分析の数値と会計上の売上原価は一致しない。これは現行仕様が既に「運用集計と会計の照合」として分けている方針と整合する

ただし**最終的には税理士またはユーザーの判断事項**であり、本推奨は確認までの仮置きである。

### 4.3 M8 — 同一商品を複数個扱うか

P0は「1 SKUに有効なInventoryUnitを1点だけ」。P1の一覧にあるのは「複数SKU」であって「1 SKU複数個体」ではない。一方 Shops CSV の必須列には `SKU1_在庫数` が含まれる。

**必要な確認事項:** 扱う商材が1点物（古着など）に限られるか、新品やセット仕入で同一商品を複数持つ運用があるか。

- 1点物に限られる → 対象外へ明記し、Shops CSVの在庫数は常に1を出力すると記す
- 複数個体がある → P1へ項目として追加する

### 4.4 M7 — 古物台帳を作るか

現行仕様は古物台帳を「隠す対象」として4箇所（権限表、Notion非送信リスト、`AC-048`）に挙げているが、生成・保存する機能はどこにもない。存在しないものを隠す条件がACになっているため、テストは必ず通るが意味がない。

**必要な確認事項:** MVPで古物台帳を作るか。

- 作らない → 対象外へ明記し、権限表とAC-048から古物台帳の記述を削る
- 作る → 仕入データモデルへ相手方確認の項目が必要になる。`docs/research/inventory-location-management-v1.md:114` に `LegalLedgerLink` の設計案がある

## 6. 判断が必要な順序
