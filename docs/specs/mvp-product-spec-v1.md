- 更新日: 2026-08-14（JST）

## 1. 目的と成功条件

### 目的

商品情報を表すSKUと、現物1点を表す在庫管理番号を中心に、仕入証憑、商品調査、撮影、画像加工、採寸、保管場所、出品文、販売チャネルへの安全な引渡し、注文、配送、棚卸、収益、会計資料までを一つにつなぐ。

### 成功条件

- 一つのSKUから、原本写真、採寸根拠、説明文候補、出品先、注文、在庫、収支、証憑、監査履歴を追跡できる。
- iPhoneでは撮影現場の次の作業が分かり、PCでは複数商品の確認・承認・例外処理ができる。
- 個人版販売チャネルでは本人が公式画面で最終操作し、非公式な自動操作を行わない。
- 外注者は担当作業だけを処理でき、不要な住所・原価・利益・税務資料を閲覧できない。
- AIは候補と根拠を提示し、人が確認した値だけを確定データとして扱う。
- 会計ソフトへ渡す直前まで整理できるが、税額・申告区分・申告完了をAIが決めない。
- 在庫中の現物は、在庫管理番号、現在の部屋・棚・段・箱／位置、案内写真、移動履歴から担当者が迷わず見つけられる。

## 4. MVP対象範囲

MVP（最初に価値を検証する最小版）は、架空または試験用の商品1点を、仕入から会計CSV準備まで通せる縦方向の一連機能とする。

1. ログイン、事業所、役割、招待、権限。
2. ホームCと、役割別の「自分の担当」。
3. 仕入バッチ、レシート画像、OCR候補、商品分割、取得原価配賦。
4. JAN・タグOCR、商品候補、公式検索への引渡し、比較根拠、人による結論。
5. 写真撮影、原本保管、必要ショット確認、カテゴリ別採寸、タグOCR、人の確定。
6. 非生成の標準画像レシピ、外部バッチ加工用ZIP、加工済ZIP再取込、SKU照合、原本比較、承認。Photoroom Proは利用者の既存契約・利用権が確認できた場合だけ選択肢にする。
7. AIの商品名・説明文候補、根拠、不足検査、人による承認。
8. 個人版向けコピー・画像書出し・公式画面引渡しと、公開後URLの本人確認登録。
9. Shops向け公式形式CSV・画像書出し。契約APIは未接続状態と前提条件だけ実装する。
10. 在庫管理番号、場所階層、部屋／正確位置の写真、商品・場所ラベル、格納、移動、棚卸差異、返品隔離。
11. 注文、在庫引当、商品＋場所の二重読取ピッキング、梱包証拠、発送、返品・キャンセルの基本記録。
12. 単品・キャンペーンの価格案、採算下限、承認、本人反映確認、Shops更新CSV。
13. 月間収支、仕入先分析、在庫年齢、データ欠損、運用集計と会計の照合。
14. 証憑、仕訳候補、人の承認、Money Forward形式CSVと出力履歴。
15. Notionへの非機密メタデータ一方向ミラー。
16. 担当、引継ぎ、承認、差戻し、通知、監査ログ、オフライン再送。

### 実装順と停止条件

MVP全体はP0とP1に分ける。どちらもDraft PRの対象だが、P0が未完成のままP1へ進まない。

- P0・縦導線: オーナー＋外注役1名＋在庫責任者、試験SKU1点について、仕入証憑→在庫番号発行→場所写真付き格納→写真/採寸→文章候補→個人版の本人引渡し→手入力注文→商品＋場所の二重読取→発送→棚卸差異確認→収益事実→仕訳候補/会計CSVを通す。権限、監査、オフライン、原本保護を含む。
- P0合格条件: AC-001、003〜008、013〜014、018〜023、025〜026、028〜034、042〜055がすべて合格し、重大・高重要度の未解決が0件である。
- P1・運用拡張: ホームC、複数SKU、画像バッチ、商品根拠、Shops CSV、価格案、仕入先分析、Notionミラー、プラン権限、チーム引継ぎ、箱の中身一括移動、複数拠点間移送、最短ピッキング順、ラベル印刷拡張を追加する。専用プリンター、RFID、GS1は機器・契約・運用確認まで接続OFFとする。
- P1合格条件: 残る全ACと技術仕様の全TAが合格する。
- `shops_csv`、`notion_projection`、`price_campaign`、`batch_image_import`、`team_advanced`、`inventory_advanced` はサーバー側機能フラグを持ち、未検証時は既定OFFにする。
- P0の代表E2E、権限越境、財務fixture、原本/監査保護のどれかが失敗した場合はP1着手を停止する。

- 自作の一括画像加工エンジン。MVP後に差し替え可能な境界だけ作る。
- 契約・書面承認・クライアント識別子発行前のShops API本番接続。
- 真贋鑑定、商品・素材・洗濯表示・相場・最終価格のAI自動確定。
- LiDAR等による無確認の自動採寸。人が実測した値を正本にする。
- AIによる税務助言、申告区分・税区分・棚卸評価法の決定、申告書作成・提出。
- 本番公開、PRマージ、実利用者への通知、課金開始。

## 7. 機能要件

### 商品・仕入

- 受入時に不変のSKUを発行し、仕入バッチと証憑へ紐付ける。
- OCR結果は原文、候補、信頼度、修正者、確定値を分離する。
- ロット費用は配賦方法、計算結果、端数、承認者を保存する。
- 原価未配賦SKUを粗利益ランキングから除外し、件数と額を表示する。

### 商品調査

- JAN/GTIN、タグ、型番、OCRは検索候補を作るだけとする。
- 利用者が公式検索画面を開き、比較対象URLと表示条件をアプリへ共有する。
- 販売中希望価格と売却済みとして観測した価格を分ける。
- 採用・除外、理由、確認日時、送料、状態、一致度を保存する。

### 写真・採寸

- 原本を上書きせず、派生画像と別管理する。位置情報は出品用派生から除去する。
- 必要ショット、欠損、重複、アップロード状態を表示する。
- トップス、アウター、パンツ、スカート、ワンピース、ニットをMVPテンプレートに含める。
- 靴、バッグ、帽子は拡張テンプレートとして含め、未対応形状はカスタム項目で継続できる。
- 数値、単位、平置幅/一周、測定状態、測定者、証拠写真、定義版を保存する。

### 画像加工

- MVPの標準レシピは白背景、中央配置、余白、出力サイズ等の非生成処理とする。
- 加工用ZIPと取込用マニフェストにSKUと画像役割を含める。
- 再取込時はSKU・件数・ファイル形式・重複を検査する。
- 原本/加工後で輪郭、色、ロゴ、タグ、傷・汚れを人が比較承認する。
- 処理方法を `manual_photoroom`、将来の `internal_engine`、許諾後の `official_api` として差し替えられるようにする。

### 出品・価格

- AI文章は候補、参照した確定項目、未確認項目を表示する。
- 個人版はコピーと画像書出し後、本人が公式画面で保存・公開・価格変更する。
- Shopsは公式形式CSVを生成し、人がプレビューして公式管理画面へアップロードする。
- 赤字、費用未入力、販売済み、入札後、重複、公式セール中等の対象を停止または除外する。
- 公式機能以外では「値引き」「セール」等の表示規則に反する文言をブロックする。

### 在庫ロケーション

- ProductSKU（商品情報）とInventoryUnit（現物1点）を分け、P0では1 SKUに有効なInventoryUnitを1点だけ紐付ける。
- InventoryUnitにはworkspace内で重複しない変更不可の `inventory_number` を発行する。メーカーJAN/GTINは参考属性であり、在庫個体番号に使わない。
- 場所は `拠点 → 部屋 → ゾーン → 棚／ハンガーラック → 段 → 箱／位置` の親子構造とする。各場所は現物を直接置けるか、単品専用か、最大点数、カテゴリ混載可否を持つ。P0の箱は固定場所として扱い、箱ごとの中身一括移動はP1とする。
- 各部屋に入口から見た全景写真、棚・段・箱／位置に正確な位置写真を持たせ、パンくずと一緒に表示する。表示用写真からGPS、所有者、撮影時刻等の不要メタデータを除去し、人物、表札、配送伝票、鍵・暗証設備を含む写真は差し戻す。
- 商品と場所のラベルには内部QRと人が読める短いコードを併記する。QRは種類、推測困難な内部トークン、版、チェック値だけを持ち、住所、原価、氏名、認証秘密を含めない。token hashは全体で一意、短いコードはworkspace内の有効ラベル間で一意、対象/種別ごとの有効版は1件だけとし、再発行時に旧版を失効する。読取後もサーバーで権限を確認する。
- P0のラベルは画面表示と一般的なA4/PDF印刷、またはチェック値付き番号の手書き運用で完了できる。専用ラベルプリンターや機種固有連携は前提にしない。
- 格納、移動、ピッキングは `商品を読む → 場所を読む → 人が内容確認` を必須とする。操作ごとの期待InventoryUnit、現在地/移動先、商品/場所ラベル版、読取日時、確認者を1回限りのscan sessionへ保存し、欠落、不一致、旧版、別操作からの再利用、未確認では確定を停止する。
- 棚卸は場所を先に読み、その場所の商品を連続読取する。開始時の移動sequenceと期待対象を固定し、開始後の通常移動は別表示する。一致、未発見候補、誤棚、予定外発見、重複、読取不能を分け、差異だけで現在地や数量を自動変更しない。
- 紛失確定、廃棄、数量調整は実行者と異なる在庫責任者またはオーナーが理由付きで承認する。
- カメラ拒否・非対応時は、チェック値付き管理番号の手入力と人の確認で継続できる。
- オフライン時の格納・移動は端末で `同期待ち` と表示し、サーバー確定と同一視しない。再送競合時は現在地を上書きせず再読取を求める。

### 注文・配送・返品

- 注文とInventoryUnitを一意に紐付け、同じ現物の二重引当を防ぐ。
- ピッキングは商品QRと現在場所QRの一致後だけ完了できる。梱包、発送でも担当、日時、状態、証拠を残す。
- 返品時は必ず返品隔離場所へ入れ、人が状態を検品してから再格納、廃棄候補、確認待ちを選ぶ。原価と移動履歴を保持する。
- 住所は発送担当へ必要期間だけ表示し、閲覧を監査する。

### 収益・会計

- 入金、売上、返金、商品原価、商品粗利益、手数料、送料、取引貢献利益を別項目で持つ。
- 金額はJPYでは1円を最小単位とする整数で保存し、浮動小数点を使わない。通貨、税込/税抜/不明、負担者、取得元、取得元の金額意味、丸め規則版を併記する。
- 注文時価格、販売者負担割引、チャネル負担クーポン、販売者の商品収入（返金前）を別項目にする。取得元が値引後金額なら、同じ値引きを再度控除しない。
- 成功済み返金は取消イベントとして元イベントを参照し、返金後の取得元金額なら同じ返金を再度控除しない。申請中、取消、手数料返還、在庫復帰も別イベントにする。
- 正味商品売上、純売上原価、商品粗利益、取引貢献利益は `docs/research/product-research-pricing-operations-v4.md` の正規化定義と同じ版管理済みdomain関数で計算する。
- 未販売品の原価は在庫へ残し、入金月と売上計上候補月を混同しない。
- 指標へ母数、観測期間、欠損、最終同期を併記する。
- AI仕訳候補は原資料、抽出事実、ルール版、根拠、承認状態を表示する。
- CSVは列、貸借一致、重複、文字コード、行数、未解決を検査し、出力バッチを不変履歴にする。

### 共通原則

- AI候補、担当者入力、承認済み確定値を上書きで混ぜない。
- 重要な変更は変更前・変更後、実行者、承認者、日時、理由を保存する。
- 外部同期には冪等キー（同じ送信を二重登録しない識別子）を使う。
- 削除は監査・法定保存・復元要件を確認し、即時の物理削除を標準にしない。

### 重要状態遷移

共通ラベルだけで制御せず、対象ごとに許可元、許可先、実行役、前提、副作用を定義する。

| 対象 | 許可遷移 | 実行役・前提 | 必須副作用 |
|---|---|---|---|
| InventoryUnit | `received → inspection_pending → putaway_pending → available → reserved → picked → packed → shipped` | 受入/在庫/発送担当。商品・場所読取、権限、active予約、対象版一致 | 追記型InventoryMovement、現在地、AuditEvent、outboxを同一transactionで保存 |
| InventoryUnit | `reserved/picked → available` | オーナー/注文担当。取消または引当解除理由、現物の再格納確認 | 予約解除、格納先、取消参照、AuditEvent |
| 場所 | `active ↔ suspended → retired` | 在庫責任者。子場所・在庫・作業中セッションの検査 | 既存在庫を自動移動せず、影響対象とAuditEventを作る |
| 棚卸 | `draft → counting → reconciliation → approved` | 棚卸担当と承認者を分離。開始時点と対象場所を固定 | 全読取、差異、再確認、解決理由を追記保存 |
| 返品 | `shipped → return_received → quarantined → inspection_pending → putaway_pending/available/disposal_pending → disposed` | 発送/在庫/オーナー。返品事実、隔離場所、人の検品、廃棄の別承認 | 元履歴を消さず返品・原価候補・在庫移動を追記 |
| 承認 | `draft → pending → approved/rejected/changes_requested` | 提出者と承認者を分離。対象版が不変 | Approval、対象版、判断理由、AuditEvent |
| ExportBatch | `preparing → ready → downloaded → confirmed` | 承認済み対象だけ。検査0件 | manifest/hashを固定し、再試行は同一結果 |
| ExportBatch | `preparing/ready → failed/expired` | 検査失敗、期限切れ、取消 | 元データを保持し参照IDと再試行可否を記録 |

- P0では同一SKUの有効InventoryUnitを1件だけにし、同一InventoryUnitのactive予約はDBの部分一意制約で1件だけにする。
- 同一の冪等キーと同一payload hashは同じ結果を返し、同じキーでpayload hashが違う要求は競合エラーとして拒否する。
- 無効な飛び越し、自己承認禁止対象、古い版への承認、同時実行競合はAPIとDB制約の両方で拒否する。

## 9. 役割・権限・外注

| 役割 | 主な許可 | 標準で非表示 |
|---|---|---|
| オーナー | 全機能、承認、設定、出力 | なし |
| 撮影・採寸 | 担当SKUの写真、採寸、コメント | 購入者情報、利益、税務 |
| 検品・出品 | 商品情報、文章候補、出品準備 | 購入者住所、会計資料 |
| 在庫責任者 | 場所、写真、ラベル、担当範囲、差異解決、棚卸承認 | 不要な購入者情報、古物台帳本文、税務判断 |
| 格納・移動 | 割当InventoryUnitと場所枝の読取、格納・移動候補、場所写真候補 | 原価、利益、全在庫出力、場所階層変更、数量調整、廃棄確定 |
| 棚卸 | 割当場所のブラインド計数、差異報告、再確認 | 提出前の期待数量、原価、利益、差異の自己確定 |
| 発送 | 引当SKU、期限、期限付き住所 | 取得原価、利益、税務 |

- 招待期限、権限変更、住所閲覧、CSV出力を監査する。
- 担当解除後は期限付き情報へアクセスできない。
- 外注の場所権限はLocationNodeの枝と作業種別へ期限付きで割り当て、別の部屋・棚・商品への読取とAPI操作を拒否する。

## 10. 連携境界

- 個人版: 画像・文章・チェックリストを準備し、本人を公式画面へ引き渡す。認証情報・Cookieを受け取らない。
- Shops CSV: 公式形式のCSVと画像を生成し、人が公式画面でプレビュー・アップロードする。
- Shops API: 契約、書面承認、クライアント識別子、現行仕様の確認後だけ機能フラグで有効化する。
- Notion: 自社DBを正本とし、schema版、公開workspace ID、SKU、定型状態、管理alias、期限、定型issue code、更新時刻、revision、archiveだけを一方向で送る。自由記述、URL、住所、氏名/メール、画像、場所名・場所階層・位置写真・ラベルトークン、原価/価格/利益、古物台帳、税務資料、秘密情報を送らない。
- 会計ソフト: 人が承認した候補だけをCSVへ出す。取込結果は人が確認して記録する。
- 外部画像バッチ: P0では任意。加工なしの安全な派生画像書出しでも縦導線を完了できる。利用者が既にPhotoroom Proの利用権を持つと確認した場合だけ `manual_photoroom` を有効にする。ProとAPIを同一契約と扱わず、公式APIは許諾・契約後だけ使う。

## 11. 税務AIの境界

### 許可

- 証憑OCR、事実抽出、算術、重複・欠損・不一致の候補検出。
- ユーザーまたは税理士が承認したルールによる仕訳候補。
- 一般情報、根拠、確認すべき質問、CSV形式チェック。

### 禁止

- 個別事情に基づく税務助言、申告方式や税区分の自動決定。
- 棚卸評価、家事按分、インボイス区分、控除可否の無確認確定。
- 「節税できます」「申告完了」「税額確定」等の断定。
- 税理士への確認が必要な事項を、AI回答だけで解決済みにすること。

固定文言: `AIは仕訳候補と一般情報を提示します。個別の税務判断は本人または税理士が行います。`

## 13. エラー・オフライン・監査

- iPhoneはオフライン保存し、再送状態、件数、失敗理由、再試行を表示する。
- 写真の部分送信や重複送信でも、原本を失わず、同じファイルを重複登録しない。
- 外部CSV/API/Notion連携の失敗はSKU単位で再試行できる。
- エラー文は「何が起きたか」「失われていないか」「次に何をするか」「参照ID」を示す。
- 監査ログは通常画面から編集・削除できず、時刻、主体、対象、操作、前後、理由、承認を持つ。
- 監査ログの差分は安全な項目名、秘匿化した要約/ダイジェスト、対象参照IDだけに限定する。住所、token、Cookie、証憑本文、AI入力全文、秘密値の前後値を保存しない。
- 通知には機密情報を本文表示せず、権限確認後の画面へ誘導する。
- 在庫ラベルの読取不能、旧版、別workspace、別種別、場所不一致は明確に区別し、手入力または再発行へ案内する。
- オフラインの格納・移動は `同期待ち` とし、同期前の場所をサーバー確定値として表示しない。競合時は予定場所と現在場所を並べ、再読取または在庫責任者への差異依頼を求める。

## 14. 受け入れ条件

- AC-001: 権限を持つ利用者がSKUを作成し、仕入証憑から会計出力まで同一SKUを追跡できる。

- AC-006: 採寸値に定義版、単位、基準、測定者、証拠が保存され、AIだけで確定しない。
- AC-007: 2回差が閾値を超えた採寸は要確認となり、理由なしで承認できない。
- AC-008: OCR/商品候補/相場根拠は候補表示で、人の結論と別フィールドに保存される。

- AC-012: 画像処理providerを変更しても、同じジョブ・レシピ・結果・監査契約を使える。

### リスク

- 販売チャネル、会計CSV、外部画像APIの仕様変更。
- 写真・証憑・住所・収支を同一サービスで扱うことによる情報漏えい影響。
- AI候補の誤りを確定値と誤認するUI。
- WindowsだけではiOS実機ビルドとApp Store要件を検証できない。
- MVP範囲が広く、縦導線の完成前に画面数だけ増えること。
- 位置写真に住居、人物、配送伝票、鍵等が写り、保管場所の安全性を損なうこと。
- ラベル破損、貼り間違い、通信切断により現物とシステム上の場所がずれること。

### 未確認

- サービス名、ブランド、価格、月間上限、保存容量、履歴保持期間。
- 法人/個人事業の初期対象、古物商運用の詳細、実際の税務設定。
- Shops APIの契約可否・料金・審査・現行仕様。
- Photoroom APIの顧客向け組込み許諾・料金。
- iOS配布方式、Apple Developer契約、対応OS・対応端末の下限。
- GitHub owner/name/visibilityは `komatsu-dev-jp/resale-ops-app/private` を提案済みだがユーザー未承認。GitHub CLI認証は無効。
- 実際の拠点数、部屋・棚・ハンガー構成、混載・容量規則、在庫件数、保管場所の通信品質。
- 使用するラベル用紙、プリンター、耐久性、貼付位置、必要なCode 128併記。

## 17. 再承認条件

- 個人版の本人操作境界、外部サービスの公式経路を変える。
- 自作画像加工またはShops APIをMVP必須へ前倒しする。
- AIへ商品、価格、税務、公開を自動確定させる。
- Notionを正本へ変える、または機密情報をNotionへ送る。
- 対象ユーザー、標準ホーム、課金区分、主要導線を変える。
- 実装中に新しい有料契約、外部書込み、公開、データ移行が必要になる。

## 18. MVP後ロードマップ

1. 自作の非生成一括画像加工エンジンを同じprovider境界へ追加する。
2. 許諾・契約後にPhotoroom公式APIとShops公式APIを段階的に有効化する。
3. 靴・バッグ・帽子・アクセサリー等の採寸テンプレートを実測で改善する。
4. 会計ソフトの追加形式、税理士レビュー、締め処理を拡張する。
5. 複数販売チャネルは、各公式API/CSV/規約を個別確認してから追加する。
6. チームの作業負荷、SLA（期限目標）、保存済みビュー、詳細分析を拡張する。
7. 箱の中身一括移動、複数拠点間移送、最短ピッキング順、循環棚卸、ラベル印刷を拡張する。
8. 対応機器・契約・取引先要件を確認後、専用プリンター、RFID、GS1 GLN/SSCC/GRAIを機能フラグで追加する。
